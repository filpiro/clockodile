# 2. Note Summaries come from a local coding-agent CLI, not an API key

Date: 2026-09-07

## Status

Accepted

## Context

A Note often starts life as a pasted client email. Reading a day's Report means
scrolling past those walls of text to find what the work actually was. The
wanted behaviour is one button that replaces the paste with a single Italian
line of at most fifteen words.

That needs a language model. Clockodile is a single-user, local-only desktop
app with no server, no accounts, and no network configuration anywhere in it —
so how the model is reached is the whole decision.

Options considered:

- **Call a provider's HTTP API directly.** The obvious shape, and the worst fit
  here. It means a settings field holding an API key, which means deciding where
  that key lives (the SQLite file next to the time entries? the OS keychain, and
  a keychain dependency per platform?), what happens when it leaks, and how the
  user gets one in the first place. It also makes Clockodile a thing that talks
  to the internet, which today it is not.
- **Bundle a local model.** Hundreds of megabytes of weights inside a time
  tracker, for one fifteen-word sentence a few times a day. Not seriously
  considered.
- **Spawn a coding-agent CLI already installed on the machine.** The user
  already has Claude Code, Codex, or OpenCode set up and authenticated for their
  own work. Clockodile spawns it, writes a prompt to stdin, reads a line from
  stdout. No key, no network code, no auth flow, no dependency.

The third option's cost is that the machine's shape becomes Clockodile's
problem. On the development machine here, none of the three CLIs exist on
Windows — all of them live inside WSL, under `~/.local/bin`, `~/.nvm/...`, and
`~/.opencode/bin`. Worse, `wsl.exe -e claude` fails with
`execvpe(claude) failed: No such file or directory`: those directories are put
on PATH by the shell's own startup files, so only a *login* shell
(`wsl.exe -e bash -lc "..."`) can find them.

## Decision

Note Summaries are generated by spawning a local CLI. Three providers are
supported — Claude Code, Codex, OpenCode — chosen in Settings, off by default.

Claude Code gets typed selects (model Sonnet|Opus, effort Low|Medium|High,
defaulting to Sonnet + High) because its accepted values are a closed, stable
set. Codex and OpenCode get two free-text fields each, passed through to `-m`
and to `-c model_reasoning_effort=` / `--variant` respectively. Their model
names change faster than this app will be updated, and a stale hardcoded list
is worse than a text box.

The prompt always travels over **stdin**, never as an argument. The prompt
contains an entire pasted email — arbitrary user text, potentially megabytes of
it, certainly containing quotes and newlines. Keeping it off the command line
removes both the length limit and the escaping problem in one move.

WSL Mode, shown only on Windows, routes the command through
`wsl.exe --cd <tmp> -e bash -lc "<command>"`. With WSL off, the binary is
executed directly with an argument list and no shell at all.

Because WSL Mode builds a shell command *string*, the free-text model and
effort fields become an injection surface. They are defended twice: validated
against `^[A-Za-z0-9._/-]+$` when Settings are saved, and single-quoted with
`'` escaped as `'\''` when interpolated. The validator exists to give an honest
error; the quoting is the actual defense.

Saving Settings runs `<cli> --version` — through WSL if enabled — and blocks
the save if it fails. Existence is checked, authentication is not: a real call
would make `Salva` take half a minute and the result would be stale by the next
generation anyway.

Settings persist as columns on the existing single-row `Settings` table, schema
5, added with `addColumn` exactly as `themeMode` was in schema 4. Model and
effort are stored per provider, so switching provider and back loses nothing.

## Consequences

Clockodile still holds no credentials and still opens no sockets of its own.
Whatever the user authenticated their CLI with is what gets used, and revoking
it is done where they set it up.

The feature is unavailable to anyone without one of these CLIs, and there is no
fallback. This is accepted: the app is a personal tool for a developer who has
them.

Failures are the CLI's, surfaced not swallowed. A non-zero exit, a 60s timeout,
or an empty result all leave the Note exactly as it was and show the CLI's
first stderr line. The user's text is never destroyed by a failed generation —
only by a successful one, which is the point of the button.

A successful generation *is* destructive and deliberately so. The pasted email
is overwritten with no undo and no second column, because the original is still
in the user's mail client. Adding an undo would mean keeping the pre-generation
text somewhere, and the cheapest place to keep it is nowhere.

Codex's output needs parsing where the others do not. `claude --output-format
json` yields one object with a `result` field and `opencode --format json` is
similarly direct, but `codex exec --json` emits a JSONL event stream; the answer
is the last `agent_message` event, with trimmed raw stdout as the fallback when
no line parses. This is the one piece of provider-specific fragility accepted,
and it is covered by a unit test.

Two limits are known and accepted:

- **The CLIs are agentic, not completion endpoints.** They can read files, run
  tools, and take far longer than a summarisation warrants. They are run with
  cwd set to a temp directory to give them nothing interesting to find, and
  killed at 60 seconds. A future CLI version could still surprise us with an
  interactive prompt on a non-TTY stdin; the timeout is the backstop.
- **WSL Mode is a boolean, not a distro picker.** `wsl.exe` gets whatever the
  default distribution is. A machine with several distributions and the CLIs in
  the non-default one cannot be configured. Adding a distro field is a one-line
  change if anyone hits it.
